# CorrectClick — Developer Notes

## Project overview
macOS menu-bar app + Finder Sync Extension that adds a "CorrectClick" submenu to the Finder right-click menu for quick file creation. See the project spec at the top of any conversation for full feature details.

## Structure
- **CorrectClick/** — parent app (menu-bar only, `LSUIElement = YES`)
- **CorrectClickExtension/** — Finder Sync Extension (`FIFinderSync` subclass)
- **project.yml** — xcodegen spec; run `xcodegen generate` after editing it to regenerate the `.xcodeproj`

## Build
```
xcodegen generate   # only needed after editing project.yml
xcodebuild -scheme CorrectClick ...
```
Open `CorrectClick.xcodeproj` in Xcode. Both targets use Automatic signing — the developer team must be set in Xcode's Signing & Capabilities (or via `DEVELOPMENT_TEAM` in project.yml).

## SourceKit false positives
SourceKit reports errors for `FIFinderSync`, `FIFinderSyncController`, `FIMenuKind` etc. because it doesn't index the FinderSync framework outside of Xcode. These are not real errors — the project builds and the symbols resolve correctly.

## Current status
**Feature complete**, plus Epics 1/7/2/3 (Phases 1–3) and Epics 4/5/6 (Phase 4 — clipboard actions, Finder utilities, format conversion) from the feature backlog agents were given. The extension is working:
- Right-clicking any folder in Finder shows a "CorrectClick" submenu
- File-creation actions: New Text File, New JSON File, New Python File, New CSV File, New Markdown File, New Shell Script (created executable), New YAML File, New HTML File (minimal boilerplate), New TOML File, New XML File, New .gitignore File, New LICENSE File, New .env File, New Dockerfile, New Swift File, New SQL File, New .plist File — plus New Text File from Clipboard and New PNG from Clipboard
- Files are created with auto-incrementing names (Untitled, Untitled 2, etc.; extensionless/dotfile types like `.gitignore` and `LICENSE` increment the same way — `LICENSE`, `LICENSE 2`, …)
- After creation, Finder selects the file and enters rename mode
- **Menu Items preferences:** the menu bar icon's "Preferences…" window (General / Menu Items / Snippets tabs) lets users hide/show and reorder any built-in menu action (two sections: New File, From Clipboard). Deleting isn't possible, only hiding, per the requirements doc. The `.gitignore`/`LICENSE` language/license pickers called out as a stretch goal (Epic 1a) were **not** implemented — both ship as empty files for now.
- **Snippets (custom templates):** the Preferences window's Snippets tab lets users define their own "New [X] File" menu entries — name, extension, starter content — with add/edit/delete/reorder/enable-disable and a live preview using dummy values. Starter content supports `{{date}}`, `{{time}}`, `{{datetime}}`, `{{filename}}`, `{{clipboard}}`, `{{author}}` placeholders (unknown placeholders are left as literal text, never stripped or crashed on). `{{author}}` is set once on the General tab. Enabled snippets appear as a third menu section, below "From Clipboard", ordered by their sort order. Import/export round-trips a JSON file of all templates via Export…/Import… buttons (merge-by-id on import, so re-importing a previously exported file is idempotent).
  - **Known limitation, not a bug:** `{{filename}}` resolves to the auto-generated stem the file is created with (e.g. "Untitled 2"), not whatever the user renames it to — Finder Sync extensions have no API to observe when an interactive Finder rename completes, so the true final name can't be known at content-write time. Documented per the requirements doc's explicit allowance to document this rather than solve it.
  - **Bug, fixed, found via manual testing:** clicking Add used to present a small blank white square that locked the whole Preferences window with no way to dismiss it short of force-quitting. Cause: `SnippetsPreferencesView` drove the sheet with `.sheet(isPresented:)` plus a *separate* `editingTemplate` optional set right before it — two independently-updated `@State` vars, which SwiftUI on macOS doesn't guarantee are observed together. If the sheet's content closure ran before `editingTemplate` was seen as non-nil, `if let editingTemplate { ... }` had no `else`, silently rendering `EmptyView()` — a sheet with zero content and, critically, no Cancel button anywhere in it. Fixed by switching to `.sheet(item: $editingTemplate)`, which ties presentation to one `Identifiable` optional (`UserTemplate` already conforms) instead of two variables that can drift apart — this removes the race entirely rather than papering over it. Verified via `System Events` UI scripting driving the actual running app: open→fill→Save and open→Cancel both now work and the sheet reliably dismisses.
- **Auto-update (Sparkle):** the menu bar icon has "Check for Updates…", and the Preferences window's Updates tab has an automatic-checks toggle (daily) + a manual "Check for Updates Now" button. Full details — feed URL, signing key handling/rotation, the sandboxing setup — are in `RELEASING.md`, not repeated here. Short version: **the repo had to be made public** for the feed and DMG links to be fetchable without auth. Notarization (needed for the install step to reliably pass Gatekeeper) is done — see "To do" item 4 below.
- **Clipboard actions (Epic 4):** New File from Clipboard (Auto-Detect) — a URL becomes a `.webloc`, JSON-parseable text becomes a pretty-printed `.json`, anything else becomes `.txt`; New JPG from Clipboard alongside the existing PNG action; New QR Code from Clipboard (`CIQRCodeGenerator`, no third-party dependency); Copy as Base64 on a selected file. **WebP was not added** — `NSBitmapImageRep` has no WebP encoder, and a third-party codec for one image format wasn't judged worth it; documented rather than silently dropped.
- **Finder utilities (Epic 5):** Copy POSIX Path / Shell-Escaped Path / `file://` URL / Markdown Link (multi-selection joins with newlines); New Terminal Tab Here (iTerm2 if installed at `/Applications/iTerm.app`, else Terminal.app — both scripted via `NSAppleScript`, on the extension's own apple-events entitlement); Copy File Hash (MD5 + SHA-256 via CryptoKit, verified against known test vectors); Compress to ZIP / Extract ZIP (via the ZIPFoundation SPM dependency — pure Swift, no subprocess); Bulk Rename (find/replace or sequential numbering, with a preview-then-confirm flow, `NSAlert` + accessory view). **`.tar.gz` extraction was not added** — needs a tar-container reader on top of gzip decompression, out of scope for the one approved archive dependency (ZIPFoundation, zip-only); documented rather than silently unsupported.
  - **Bug, fixed, found via manual testing:** Bulk Rename silently did nothing — no dialog, no crash. Finder invokes menu-action selectors on a **background thread**; building an `NSAlert` there throws, and `FIFinderSync` catches the exception and drops it (the only trace is `FIFinderSync caught an exception while executing selector` in `/usr/bin/log show --predicate 'process == "CorrectClickExtension"'`). Hopping to the main thread wasn't enough on its own: the extension is a `BackgroundOnly` process, so `NSApp.activate` is a no-op and the alert opened *behind* the front Finder window with no keyboard focus. `BulkRenameUI.run` now hops to main, switches to `.accessory` activation policy before activating, and afterwards restores `.prohibited` and re-activates Finder (plain `deactivate()` left the windowless extension as the front app). Any future extension-side UI needs the same three steps. Verified by driving the installed Developer ID build with `System Events`: keyboard-only find → Tab → replace → Return → Return renamed the files and returned focus to Finder.
- **Format conversion (Epic 6):** CSV → JSON and JSON → CSV on a selected file, both fully unit-tested per the requirements doc's explicit call for tests on this kind of logic — including a hand-rolled order-preserving JSON parser (`Shared/OrderedJSONParser.swift`), written because `JSONSerialization`'s `[String: Any]` has no key-order guarantee, which would otherwise make JSON → CSV's column order nondeterministic between runs. **YAML ↔ JSON and Markdown → HTML were explicitly descoped** (would have needed the Yams/Ink SPM dependencies — deferred by product decision, not a technical blocker).
- All Epic 4/5/6 selection-based actions appear as a fourth menu section ("File Actions" in Preferences) that only shows when the current Finder selection actually makes sense for that action — e.g. "Extract ZIP" only for a single selected `.zip`, "Copy as Base64"/"Copy File Hash" only for exactly one selected file. That gating logic (`Shared/FileUtilityApplicability.swift`) is separate from and additional to the existing enabled/order preferences, and is itself unit-tested.

## Known limitations
- **No right-click menu in iCloud Drive / OneDrive / Dropbox folders — use the toolbar button there.** Since macOS Sonoma, Finder doesn't show *any* Finder Sync extension's contextual menu inside File Provider locations (iCloud Drive and everything under `~/Library/CloudStorage`). Apple has confirmed this is by design (developer.apple.com/forums/thread/718381 and /737283). An earlier version of this note blamed "first extension registered for a folder wins" — that's **not** the cause: on the dev machine, OneDrive's own Finder Sync extension is disabled and iCloud Drive has none, yet the menu still doesn't appear. Apple's suggested alternatives (`FileProviderUI`, `NSFileProviderCustomAction`) only work inside a File Provider domain you own. **Workaround, implemented:** Finder Sync *toolbar buttons* still appear in those locations, so the extension provides one (`toolbarItemName`/`toolbarItemImage` in `FinderSync.swift`) with the same menu, listed flat rather than inside a "CorrectClick" submenu. Users add it via Finder's View → Customize Toolbar…; onboarding step 3 and the README explain this. Other similar apps handle it the same way. Not verified yet: the toolbar button inside a OneDrive (`~/Library/CloudStorage`) folder specifically — Apple's thread only confirms iCloud Drive.

## Entitlements notes
- Parent app: sandboxed. It used to hold a Terminal `apple-events` temporary exception (+ `NSAppleEventsUsageDescription`) for an "Uninstall CorrectClick…" menu item that scripted Terminal to run a bundled uninstaller; the menu item was removed by product decision, and the entitlement and usage string with it.
- Extension: sandboxed (`app-sandbox = true`) + `temporary-exception.files.absolute-path.read-write` with path `/` — this grants full filesystem read-write within the sandbox and is valid for notarised direct-download distribution. **App Store distribution would require a different architecture** (XPC relay: extension calls parent app via XPC, parent app holds user-selected file access and does the actual write).
- Parent app also holds `temporary-exception.files.**home-relative-path**.read-write`, scoped to `/Library/Application Support/CorrectClick/` — this is the shared menu-preferences/snippets/author-name folder (`Shared/MenuItemPreferences.swift`, `UserTemplateStore`, `AuthorPreferenceStore`). **Why this is needed:** the app and the extension are two separate processes with two separate sandbox containers, so neither one's own container is a place they can both reach. The folder has to live at a real path outside both, so both sides need an entitlement that reaches it — the extension already has one (its blanket `/` exception covers this path too, no change needed there); the app didn't, so it got this narrower one instead of widening its own sandbox further.
  - **This was broken for a real stretch of the project and only caught by manual testing, not by any of the unit tests — worth internalizing, not just fixing.** The original entitlement used the **wrong key**: `temporary-exception.files.absolute-path.read-write` with value `"~/Library/Application Support/CorrectClick/"`. `absolute-path` wants a literal, fully-resolved path and does **not** expand `~` — the sandbox matched it as a literal (nonexistent) path and silently denied every write. Confirmed with `log stream --predicate 'senderImagePath contains "Sandbox"'` showing `Sandbox: CorrectClick(PID) deny(1) file-write-create /Users/.../Library/Application Support/CorrectClick`. The fix: `home-relative-path` is the key actually meant for per-user paths — it resolves relative to `$HOME` at runtime with no `~` in the string at all. All along, `MenuPreferencesStore.save()`/`UserTemplateStore.save()`/`AuthorPreferenceStore.save()` were failing on every real (sandboxed) run — menu-item toggles, snippets, and the author name never actually persisted — while every one of their unit tests kept passing, because those tests inject a temp file `URL` directly into the store's initializer, bypassing the entitlement and the sandbox entirely. **The lesson: a green test suite here proves the store's logic is correct, not that the sandboxed path it writes to in the real app is actually reachable** — that only shows up by running the real signed app and checking the file landed on disk, which is exactly how this got caught (a user report of "Add Snippet locks up with no way out," traced with `log stream` to a sandbox deny, not to anything the tests could have caught).
- Both the app and extension resolve that shared path via `RealHomeDirectory.path` (`Shared/MenuItemPreferences.swift`), not `NSHomeDirectory()` / `FileManager.homeDirectoryForCurrentUser`. Under App Sandbox those APIs return the *container* path (e.g. `~/Library/Containers/com.correctclick.CorrectClick/Data`) even when a temporary-exception entitlement grants access elsewhere — they don't reflect what the entitlement actually unlocked. `RealHomeDirectory` reads the true home directory from `getpwuid(getuid())` instead, so both processes compute the identical real path and land on the same file. If a preferences-loading bug ever looks like "the extension and app see different files," check this first. `UserTemplateStore` (`templates.json`) and `AuthorPreferenceStore` (`author.txt`) reuse this same mechanism and folder.
- The app also holds `com.apple.security.files.user-selected.read-write`, a normal (non-temporary-exception) entitlement, for the Snippets tab's Import…/Export… buttons — they use `NSOpenPanel`/`NSSavePanel` to let the user pick an arbitrary file, which needs this even though it's unrelated to the shared-preferences path above.
- Extension also holds `temporary-exception.apple-events` scoped to `com.apple.Terminal` and `com.googlecode.iterm2` (Epic 5, "New Terminal Tab Here") — scripted via `NSAppleScript`, because `NSWorkspace.open()` can't hand a document or folder to another app under App Sandbox. Needed a matching `NSAppleEventsUsageDescription` in the extension's own Info.plist too.
- ZIPFoundation (Epic 5, compress/extract) and CryptoKit (Epic 5, file hashing) needed **no new entitlements** — ZIPFoundation is pure Swift file I/O riding on the extension's existing blanket `temporary-exception.files.absolute-path.read-write`, and CryptoKit is a local computation framework with no filesystem/network footprint. Worth stating explicitly so it isn't re-litigated later.

## Uninstalling
- **Users uninstall by dragging the app to the Trash** — there's no in-app uninstaller (removed by product decision). That removes the app and, with it, the embedded Finder Sync extension. macOS has no hook that runs code when an app is trashed, so the ~70 KB of settings in `~/Library/Application Support/CorrectClick/` and the two `~/Library/Containers/com.correctclick.*` folders stay behind — the normal Mac convention, and it means a reinstall keeps the user's snippets. The README lists the folders for anyone who wants them gone; a future Homebrew cask's `zap` stanza should list the same three.
- `scripts/uninstall.sh` (developer tool) can't fully clear `~/Library/Containers/com.correctclick.CorrectClick` when run from a plain shell/Terminal — macOS's TCC blocks that even for the owning user unless the calling app has Full Disk Access. The script warns and continues rather than aborting. This is a real platform constraint, not a bug to "fix".

## macOS 26 pluginkit quirk
On macOS 26, each new debug build is registered as a new plugin instance in a pending-approval state, even if the extension is already enabled in System Settings. A post-build script in `project.yml` runs `pluginkit -e use -i <bundle-id>` automatically after each build to approve it. Without this, the extension runs but Finder ignores it (the menu does not appear).
